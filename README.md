# sack-knowledge

個人活動のナレッジ基盤を置くプロジェクトです。副業と個人活動のメール、会議、予定、Discordの記録をローカルへ集約し、Agent Hubと将来のAI秘書が同じ窓口から検索します。本業のデータは取り込みません。

2026-11-23時点では設計とDiscordの既存DBの確認が済んでおり、実装とデータ取り込みは始めていません。

## 公開する範囲

このリポジトリは公開します。置くものは設計、コード、設定の見本です。次の3つは`local/`に置き、`.gitignore`でGitの管理から外します。

- 設定ファイル。対象のアカウント、接続先、NAS上の保存場所を書きます。
- 原本のファイルとDBのファイル。
- この環境の確認結果を書いた`local/environment.md`。

`local/`はGitに入らないため、バックアップの対象に含めます。

## 要件

ユーザーが2026-11-22に示した要件は次の4点です。

- 取り込んだ記録は基本的にすべて検索できる。
- 検索が速い。
- データ量が増え続けても使える。利用期間は10年を想定する。
- 検索時にAIが消費するトークンを最小にする。

## 保存の構成

1. 原本。取得元から受け取った内容を、取得元と年月で分けたファイルへそのまま保存します。取得元の名前、取得元でのID、アカウント、取得日時、内容のハッシュを付けます。添付ファイルと録音は実体を別の保存先へ置き、場所とハッシュだけを記録します。
2. 検索用の表。メール、発言、予定、録音の1件を1行にします。列は種別、日時、題名、参加者、スレッドや親子の関係、活動区分、削除済みかどうか、原本への参照です。本文は全文検索とベクトル検索の両方で引き、2つの順位を合成します。
3. つながりの表。人物、案件、出来事を別の表で管理し、各行から参照します。同一人物の複数の名前や、同じ会議の予定と録音は、対応を表に記録します。取得元にある送信者、宛先、参加者、スレッドから作り、AIによる抽出は使いません。
4. AI抽出情報。スレッド、会議、日ごとの要約と、人物や案件ごとの短い概要が該当します。根拠にした行のID、使ったモデル、生成日時を必ず持たせます。原本が更新または削除された場合は、対応する抽出情報を無効にして作り直します。

2から4は原本から作り直せる状態を保ちます。DBや検索方式を後から変える場合も、原本は変更しません。

## 表の定義

検索用の表、つながりの表、AI抽出情報を次の表に分けます。列の型と索引は、DBを決める段階で定めます。

| 表 | 1行の単位 | 主な列 |
|---|---|---|
| 記録 | メール1通、発言1件、予定1件、録音1件 | 取得元、アカウント、取得元でのID、種別、発生日時、取得日時、題名、本文、活動区分、削除済みかどうか、原本への参照 |
| まとまり | 検索と埋め込みの単位 | 含む記録のID、開始日時と終了日時、検索用の本文、埋め込み、埋め込みモデル |
| 人物 | 1人 | 表示名、メモ |
| 人物の別名 | 取得元での1つの名前 | 取得元、取得元でのIDまたはアドレス、人物 |
| 案件 | 1つの案件や活動 | 名前、活動区分 |
| 案件の割り当て規則 | 1つの規則 | 取得元、対象（チャンネル、ラベル、カレンダー、相手のドメイン）、案件 |
| 出来事 | 1回の会議や催し | 開始日時、終了日時、題名 |
| 記録と人物 | 記録と人物の1つの組 | 役割（送信者、宛先、参加者、メンション先） |
| 記録どうしの関係 | 記録2件の1つの組 | 関係の種類（返信、同じスレッド、同じ出来事） |
| AI抽出情報 | 要約または概要1件 | 対象の種類とID、本文、根拠にした記録のID、モデル、生成日時、状態（有効、無効、確認待ち） |
| 修正の記録 | 人が直した規則1件 | 日付、対象（要約、概要）、規則の本文 |
| 同期の状態 | 取得元とアカウントの1つの組 | 差分用のトークン、最後に成功した日時、最後のエラー |
| 許可リスト | 取り込む対象1件 | 取得元、対象、ローカル保存の可否、外部AIへの送信の可否 |

まとまりは取得元ごとに作り方を変えます。メールは引用と署名を除いた1通、Discordは同じチャンネルで時刻が近い発言の並び、録音は一定の長さで区切った文字起こしを1つのまとまりにします。Discordの発言は平均38文字で、1件ずつ埋め込むには短いため、発言の並びを単位にします。

日時は、出来事が起きた日時と、基盤が取得した日時を別の列に持ちます。保存はUTCにそろえ、予定は元のタイムゾーンも記録します。

人物の別名と案件の割り当て規則は人が管理します。AIは候補を出すだけにし、表への反映は人が決めます。

## グラフDBを最初に採用しない理由

2026-11-22の調査では、グラフ型の検索は複数の事実をたどる質問と全体を問う質問で有利でした。単純な事実の検索では、標準の検索を下回る報告がありました。多くの方式は取り込みのたびに本文をAIへ読ませます。この基盤への質問は、日時、人物、案件で絞る検索が中心になる見込みです。

履歴が長くなるとグラフ型が有利になるという2026年7月の報告が1件あります。著者1人の未再現の結果ですが、10年の利用では無視しません。つながりの表と出典を最初から持ち、グラフ層を後から重ねられる構成にします。

グラフ層を追加する条件は、複数年にまたがる傾向の質問や何段もたどる質問が繰り返し必要になることです。追加する方式の候補は2つあります。取り込み時にAIを使わない方式と、文書の削除結果が再構築と一致する方式です。

## 取り込みの規則

- 取り込む対象は許可リストで指定します。単位はアカウント、ラベル、カレンダー、Guild、フォルダです。リストにない対象は原本にも保存しません。
- 仕事と私用が混在するアカウントは、ラベル、相手のドメイン、カレンダー単位で選別します。判定できない項目は保留区画へ置き、検索対象から外します。
- 重複は、取得元、アカウント、取得元でのIDの組で判定します。
- 削除された項目は削除済みとして記録し、検索結果とAI抽出情報から外します。
- メールは返信に含まれる過去の引用と署名を検索対象から外します。

## バックアップ

バックアップの保存先はNASです。対象は`local/`の全体で、原本のファイル、DBのファイル、設定ファイルを含みます。

検索用の表、埋め込み、AI抽出情報は原本から作り直せます。人物、人物の別名、案件、案件の割り当て規則、修正の記録、許可リストは人が管理する表で、原本から作り直せません。この6つの表を失わないために、DBのファイルも保存します。

Discordの発言の原本は既存の収集BotのPostgreSQLにあり、この基盤のバックアップには含めません。

NAS上の保存場所、暗号化の方法、保存の頻度は決めていません。

## Discordの既存DB

Discordの発言はすでに動いている収集BotのPostgreSQLから読み取ります。2026-11-23に、このDBを読み取りだけで確認しました。発言の本文は読んでいません。接続先、表の名前、件数の内訳は`local/environment.md`に記録しています。設計に使った結果は次の4点です。

- 発言は約5.5万件で、1件の平均は38文字です。
- 増え方は年に約2.2万件、約80万文字です。同じ増え方が続くと10年で約22万件になり、1つのファイルのDBで扱える量です。
- 削除された発言は発言の表から行ごと消えます。Botが持つ削除の記録は、最後の記録が2026-10-06です。
- Botが持つ検索用のデータは、最後の更新成功が2026-10-06です。

この結果から、次の方針にします。

- 削除は、基盤が持つ発言のIDとBotの表にあるIDを同期のたびに比べて検出します。Botの削除の記録は2026-10-06より後の削除を記録しているかを確認できていません。
- Botの検索用のデータは使いません。まとまりと埋め込みは発言の表から基盤の側で作ります。
- 読み取り専用のロールと接続の経路はBotの側の変更になるため、ユーザーの許可を得てから決めます。

## AIからの窓口

検索と取得は1つの読み取り専用の窓口にまとめます。トークンを抑えるため、窓口は次の規則を守ります。

- 道具は検索、取得、集計の3つまでにし、説明文を短くします。
- 検索は、ID、日時、人物、題名、100文字程度の抜粋を最大10件返します。本文はIDを指定した取得でだけ返します。
- 1回の応答の文字数に上限を設けます。上限を超えた分は、続きがあることだけを返します。
- 期間、人物、案件での絞り込みと、件数や一覧の集計はDBで処理し、結果だけを返します。
- 検索はまず要約と概要を対象にし、必要な場合だけ本文を対象にします。
- 順位の合成と並べ替えはローカルで処理し、AIを使いません。
- 返す項目には、取得元、ID、日時、原本への参照を必ず付けます。

外部AIへ送る内容は、質問ごとに窓口が取り出した分に限ります。原本や表をまとめて送ることはしません。この方針はユーザーが2026-11-23に決めました。ローカルへの保存許可と外部AIへの送信許可は、別の設定として項目ごとに持たせます。

### 道具の仕様

| 道具 | 受け取るもの | 返すもの |
|---|---|---|
| 検索 | 検索語、期間、人物、案件、取得元、対象（要約か本文）、続きの位置 | 該当件数、最大10件の項目、続きの有無 |
| 取得 | 記録またはまとまりのID（最大5件）、前後に付ける記録の数 | 本文、取得元、日時、原本への参照 |
| 集計 | 集計の軸（月、人物、案件、取得元）、期間などの絞り込み | 最大50行の件数の表 |

応答の上限の初期値は、検索が2,000文字、取得が6,000文字、集計が2,000文字です。窓口は呼び出しごとに道具の名前、返した文字数、応答時間を記録し、本文は記録しません。上限はこの記録を見て調整します。

接続方法はMCPを第一候補にします。窓口は呼び出しを受けて結果を返すだけで、基盤の側から利用側へデータを送りません。利用側の仕組みはこの設計の対象外です。

外部AIへの送信が許可されていない項目は、外部AIを使う呼び出し元へ返しません。呼び出し元の見分け方は決めていません。

## AI抽出情報の検査と修正の記録

2026年9月の記事[300 AGENTS, ONE GRAPH, AND A LOOP THAT EDITS THE LOOP](https://x.com/Mr_Buzzoni/status/2096128417108287566)から、運用の規則を4つ取り入れます。記事は著者1人の経験談で、測定値を示していません。そのため、費用が小さく、後から外せる規則だけを選びました。

- 要約と概要は決まった形式で受け取ります。項目は対象のID、本文、根拠にした記録のIDです。形式に合わない出力は保存しません。
- 保存の前に、AIを使わないスクリプトで検査します。検査する点は3つあります。根拠にした記録のIDが実在すること、削除済みの記録を根拠にしていないこと、文字数が上限に収まることです。検査に通らない出力は1回だけ作り直し、2回目も通らない場合は人の確認待ちにします。
- AI抽出情報は状態を持ちます。状態は有効、無効、確認待ちの3つです。作り直す対象は無効のものと未作成のものに限ります。原本が変わっていない対象には、AIを呼びません。
- 人が直した内容は、日付を付けた1行の規則として修正の記録に残します。要約と概要を作るたびに、この記録をAIへ渡します。人物の別名と案件の割り当て規則の修正は、それぞれの表へ反映します。

週に1回、同期のエラー、検査に通らなかった出力、確認待ちの項目を見直します。AIは別名、割り当て規則、修正の記録への変更案を出すだけにし、反映は人が決めます。

記事の内容のうち、次の2つは取り入れません。記事はAIが抽出した関係を信頼度つきでグラフへ加えます。この基盤のつながりの表は、取得元にある項目だけから作ります。また、記事は多数のエージェントを並べて調査します。この基盤の取り込みは取得元との差分同期で足ります。

## 段階的な導入

1. 対象範囲を決める。Googleアカウント、ラベル、カレンダー、外部AIへの送信方針は決定済み。
2. Discordの既存DBを読み取り専用でつなぎ、検索窓口の最小版を作る。この段階で、DBの候補と日本語の検索方式を実データで比べる。
3. Googleカレンダーを許可リスト付きで追加し、予定とDiscordの会話を日時と参加者で関連づける。
4. Gmailを許可リスト付きで追加する。
5. PlaudとObsidianを追加する。
6. 要約と概要を追加する。保存前の検査と修正の記録も同じ段階で入れる。

DBの候補はSQLiteとDuckDBです。どちらも1つのファイルで全文検索とベクトル検索を併用できます。複数の機器から同時に書き込む必要が出た場合は、PostgreSQLへ移します。

第一候補はSQLiteです。同期のたびに少数の行を追加、更新する使い方で、Discordの実測から量も小さいためです。DuckDBは段階2の比較で差が出た場合に選びます。現在の量では、ベクトル検索は全件との比較で足りる見込みです。近似検索の索引は、応答時間が問題になった場合に追加します。

日本語の全文検索は方式を決めていません。SQLiteの3文字単位の方式は3文字未満の語を検索できません。単語で区切る方式と、実データで比べます。埋め込みモデルは日本語の評価セットJMTEBと実データで比べます。

## 検索方式の比べ方

段階2で、ユーザーが実際に尋ねたい質問を30問集め、答えになる記録のIDを付けます。この質問で次の3つを測ります。

- 上位10件に答えの記録が入った質問の割合
- 応答時間
- 1問あたりに返した文字数

比べる方式は3文字単位の全文検索、単語で区切る全文検索、ベクトル検索、全文検索とベクトル検索の合成です。
